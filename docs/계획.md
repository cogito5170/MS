# 계획 -- Sensor · DC · CR · Policy · Action Intent · Validate/Arbitrate/Guard · Claude Code 그림자 (2026-10-02 고침)

지금 있는 것과 역할은 [`역할.md`](역할.md). 이 문서는 **앞으로**와 **층의 경계**다.
경계는 사용자가 잡았다(2026-10-02). **WALP 는 쓰지 않는다** -- 옛 문서의 "WALP ARBITER" 는 지금의 `Arbiter` 다.

## 0. 캐시는 뜻이 아니라 바이트다 -- 그리고 그것은 CR 의 책임이다

- provider 프롬프트 캐시는 **바이트의 앞부분 일치**다. 뜻이 같아도 바이트가 하나 다르면 그 뒤는 새로 쓴다.
- 캐시 항목은 **캐시 지점**에서만 생긴다. claude -p 는 지점을 프롬프트 끝에만 둬서, 시스템 글이 같아도 사용자 글이 다르면 0 을 읽었다(실측).

| 문제 | 맡는 층 | 까닭 |
|---|---|---|
| 시스템 프롬프트의 안정된 앞부분 유지 | **CR** | 맥락 배치 문제 |
| 캐시 지점의 위치 | **CR**(선언) · **Provider Adapter**(번역) | CR 은 "여기까지 안정" 만 말하고, provider 마다의 캐시 방식은 어댑터가 안다 |
| 실제 캐시 적중 확인 | Provider Adapter + Runtime Telemetry | API 응답에서 잰다 |
| `--fresh` 같은 실험 제어 | Evaluation Harness | 제품 런타임과 떼어 둔다 |
| 적응 맥락이 정보를 숨김 | **CR** | 무엇을 보일지의 결정 |
| 숨긴 정보를 다시 꺼냄 | **CR** + Retrieval | 맥락 선택의 결과 |
| 꺼냄 때문에 지연이 늚 | Runtime Telemetry | 관측 문제 |
| 토큰 감소 대 지연 증가의 저울질 | **CR 의 Context Policy** | 맥락 예산의 결정 |
| 무엇을 할 것인가 | Policy | 의사결정 |
| 실행해도 되는가 | Guard | 안전 · 권한 |

결정 재사용(같은 상태에서 같은 결정을 다시 쓰기, 곧 **뜻의** 캐시)은 provider 캐시와 다른 것이다. CR 쪽에서 상태 해시로 한다(④).

**지금 코드(2026-10-02)**: CR 이 `CanonicalPrompt.cache_boundary="system"` 으로 선언하고, Claude 어댑터만 그것을 `cache_control` 로 번역한다.
선언이 없으면 지점을 두지 않는다. `cr.py` · `prompt.py` 에는 `cache_control` 이 없다(시험이 붙든다).

## 1. 구조

```
                 SENSOR                      외부 패키지(llmsensor). MS 는 그 구현을 소유하지 않는다
                   │  Telemetry 만            Reading · Q · 잔차. "should_search: true" 같은 판단은 내지 않는다
                   ▼
           STATE / Decision Context (DC)     MS 모형이 텔레메트리의 뜻을 정한다
                   │
                   ▼
          ┌─────────────────┐
          │       CR        │   Context Runtime / Context Resolver
          │ context select  │   Policy 가 판단하기 위해 어떤 정보를 · 어떤 순서와 꼴로 · 어디까지 줄지
          │ context budget  │
          │ prompt layout   │   프롬프트는 CR 의 출력 꼴 가운데 하나일 뿐이다
          │ cache strategy  │   "여기까지 안정" 을 선언(어떻게 캐시할지는 어댑터)
          │ retrieval       │
          │ decision record │
          └────────┬────────┘
                   ▼
                POLICY          decision rule -- 무엇을 관측하고 · 무엇을 중요하게 보고 · 어떤 조건에서 어떤 결정을 고르나
                   │            (LLM 은 Policy 를 돌리는 런타임의 하나다. LLM 을 빼도 구조가 남는다)
                   ▼
             ACTION INTENT
                   ▼
               VALIDATE         형식 · 근거가 의도를 받치나
                   ▼
              ARBITRATE         선택(selection): 후보 의도 가운데 무엇을
                   ▼
                 GUARD          허가(permission): 고른 것을 실행해도 되나
                   ▼
            ACTION EXECUTOR

  옆에서:  Provider Adapter ── Claude cache · OpenAI cache · 그 밖
           Runtime Telemetry ── 입력 토큰 · 캐시 읽기 · 꺼냄 수 · 지연 · 실패 · 비용 · 맥락 신선도  ──▶ 다음 Decision Context
```

CR 의 자리는 "Policy 다음" 으로 고정하지 않는다. **CR = Policy 가 쓸 맥락을 만드는 층**이다.

### 정의

| | 정의 | 하는 일 |
|---|---|---|
| **Policy** | decision rule | 무엇을 관측할지 · 무엇을 중요하게 볼지 · 어떤 조건에서 어떤 결정을 고를지 |
| **CR** | decision context construction rule | 그 Policy 가 판단하려면 어떤 정보를 · 어떤 순서와 꼴로 · 어디까지 줄지. 그 맥락의 비용 · 신선도 · 캐시 가능성 · 꺼냄 비용을 관리 |
| **Arbitrate** | selection | Action A 와 B 가운데 무엇을 (예: RETURN 대 CONFIRM_TARGET → CONFIRM_TARGET) |
| **Guard** | permission | 고른 A 를 실행해도 되나 (예: 배터리 < 최소? 위치가 유효? 능력이 있나? 안전 제약? → 아니면 거부) |

**CR 이 하면 안 되는 것**: 실제 Action 실행 · 안전 허가 · 최종 중재 · 도구 권한 결정 · Sensor 의 판단.

### CR 의 목적함수 -- 입력 토큰만 줄이지 않는다

적응 맥락은 지금까지 꺼냄을 늘리고 느렸다(역할.md F2: 작은 맥락 → LLM → "정보 부족" → 꺼냄 → LLM → 더 긴 지연). 그래서

```
J_CR = α · input_tokens + β · retrieval_count + γ · latency + δ · output_failure + ε · cache_miss
```

처럼 맥락 비용 전체를 본다. α…ε 는 CR 안의 Context Policy 가 정한다. **값은 아직 정하지 않았다** -- 재고 나서 정한다(④).

② Sensor → Telemetry       ✅ sensor-telemetry-1 (2026-10-02)
③ Telemetry → DC
④ DC → CR                   (CR v2: J_CR · 결정 재사용 · 덧붙이기만)

API 비용을 더 정밀하게 재기보다 **정보 흐름의 계약을 먼저 완성**한다.

### ① CR 분리 ✅

- `ms/cr.py` 가 맥락 · 프롬프트를 짓는 유일한 자리. 입력 `state + request + query results`, 출력 `ContextDecision(selected context · prompt · decision record)`.
- 결정 기록: `cr` 판본 · 맥락 판본 · 배치 · 지시문 판본 · `prefix_hash` · `cache_boundary` · 통계 · 적용 안 한 것.
- **지금은 위치를 정할 때가 아니라 입출력 계약을 굳힐 때다.** 계약이 안정되면 `cr.py` 를 그대로 별도 패키지로 뗀다.

### ② Sensor → Telemetry ✅ (2026-10-02, `sensor-telemetry-1`)

**한 것**: `ms/sensing.py` -- `to_telemetry(sense 출력) -> 신호` · `ingest(manager, …)` · `otel_events()`. 선행조사 `paper/선행조사/센서배선.md`.
받는 칸 telemetry · readings · residual / 안 받는 칸 fusion · verdict(이름만 격리함에) / **수만 받는 화이트리스트**(why · 출력 꼬리 · 경로 · 답의 값은 버림) /
모르는 칸은 버리고 이름만 `dropped` 에. 시험 13 개(진짜 llmsensor 출력에 비밀을 심은 픽스처 · 깔려 있으면 진짜 sense() 로 계약 재확인).
코드를 6 가지로 망가뜨려(why 를 신호로 · Q · 판정을 신호로 · 출력 꼬리 받기 · 화이트리스트 밖 통과 · 목록 통째로 · UNKNOWN 을 OK 로) 전부 빨개진다.
모형이 없으니 지금 Sensor 신호는 전부 **unbound** 로 격리된다 -- ③ 이 그 뜻을 정한다.

아래는 시작 전에 적은 것(그대로 둔다):

- **L0 Telemetry 가 따로 섰다(2026-10-02): [cogito5170/Telemetry](https://github.com/cogito5170/Telemetry).** 층은 L0 Telemetry → L1 Sensor →
  L2 State → L3 DC → L4 Policy → L5 Action(→ L0). MS 런타임은 그쪽 `Recorder` 로 L0 사건을 바로 낸다 -- **붙였다(2026-10-02)**: `ms/l0.py`, `Runtime(l0_ledger=…)` · `ms ask --l0-ledger`. 모형 호출 · 도구 호출 · 실행 시작/끝(+`decision_ref`). 행동(`action.*`)은 Action Executor(⑥⑦)가 서면 그쪽에서 낸다.
- 그쪽 경계 점검(`docs/TELEMETRY.md` 7 절): `RunRecord.policy`(정책 판본 · 중재 결정 · **정책이 본 상태**)는 텔레메트리 기록 안의 결정 · 상태라
  L0 규칙에 어긋났다. **뗐다(2026-10-02, 사용자 결정)**: `ms/decision_record.py` 의 DecisionRecord(내용 해시 id)로 옮기고, RunRecord 는
  `decision_ref` 만 갖는다(ms-run-telemetry-3). 원장에는 결정 줄이 먼저 · 실행 줄이 id 로 가리킨다. L0 `action.dispatch.decision_ref` 도 같은 id 를 쓴다.
- Sensor 는 L0 Telemetry 를 **선택 의존**으로 쓴다(`llmsensor.telemetry.l0`). 문턱 있는 토큰 판독은 Sensor 의 sensing 으로 옮겼다.

- Sensor 는 `pip install git+https://github.com/cogito5170/Sensor` **선택 의존**. MS 는 그것 없이도 돈다(센서 상태는 모름).
- `ms/sensing.py`: Reading · Q · 잔차를 텔레메트리 신호로만 편다(`sensor.<이름>.status` · `sensor.q` …).
- **Sensor 의 판정(Verifier 의 ACCEPT · RETRY …)과 정책 제안(token_budget · route …)은 배선하지 않는다.** 그것은 Sensor 가 이미 판단한 것이라,
  받으면 Sensor 와 Policy 의 경계가 다시 섞인다. Validate 는 MS 의 층으로 따로 짓는다(⑦).
- 시험: Sensor 출력이 그래프에 바로 안 들어간다 · 판정 칸이 들어오면 거절(격리) · UNKNOWN → 모름.
- 조사 먼저(`paper/선행조사/`): 관측 텔레메트리를 맥락 결정으로 되먹이는 선례.

### ③ Telemetry → DC

- 모형(usage-model 다음 판 또는 Sensing 모형)이 센서 텔레메트리를 해석: `outcome_confidence`(Q 의 띠 -- 보정 전이면 순서 점수로만, HIGH 금지) ·
  `false_success_risk` · `loop_risk` · `cost_anomaly`. **Runtime Telemetry**(캐시 읽기 · 꺼냄 수 · 지연 · 실패 · 맥락 신선도)도 같은 길로.
- DC = 결정에 쓰일 **상태의 묶음**(그래프의 파생 상태). 원 측정은 여기 없다.

### ④ DC → CR (CR v2)

- CR 이 DC 를 받아 맥락을 짓는다. **J_CR** 의 항을 결정 기록에 남기고(그 판의 토큰 · 꺼냄 · 지연 · 실패 · 캐시 적중), 가중치는 Context Policy 가 정한다.
- **결정 재사용**(뜻의 캐시): DC 해시가 같으면 직전 CD 를 다시 쓴다.
- **덧붙이기만**: 에이전트 하네스에서는 앞의 맥락을 고치지 않고 덧붙인다(바이트 캐시를 지킨다).
- F2 를 사전등록하고 잰다: 덜 자르면 꺼냄과 지연이 주는가.

### ⑤ Policy

- decision rule 로 세운다: 무엇을 관측할지(어느 센서 · 어느 상태) · 무엇을 중요하게 볼지 · 어떤 조건에서 어떤 결정을. 판본 · 재현(replay).
- 지금 `policy.py` 의 선택기들은 **CR 의 내부 Context Policy** 로 간다(이름 고침). Provider 선택은 Policy 에 남는다.

### ⑥ Action Intent

- LLM 의 출력(지금 `Proposal`)을 **Action Intent** 로 일반화한다: 누가 냈든(LLM · 규칙 · 사람) 같은 꼴. LLM 을 빼도 아래 층이 그대로 돈다.

### ⑦ Validate / Arbitrate / Guard

| 층 | 묻는 것 | 지금 코드에서 옮길 것 |
|---|---|---|
| Validate | 이 의도는 형식이 맞고 근거가 받치나 | A0(못 읽음) · A4(인자) |
| Arbitrate | 후보 가운데 무엇을 고르나 (selection) | A1(제안 안 된 도구) · A2/A3(본 것 · 대상) · A5(맥락 뒤 상태 바뀜) · A8(되풀이) |
| Guard | 고른 것을 실행해도 되나 (permission) | **A7(external · irreversible 허가)** · A6(사전조건 · 신선도) · 새로: 세션 상한 · 능력 · 안전 제약 |

- **Guard 모드**: `GUARD_MODE=shadow`(기록만) · `GUARD_MODE=enforce`(거부). **모드만 바뀐다** -- 안전 불변식 자체는 코드에서 빠지지 않고,
  "끄는 스위치" 가 Guard 의 판단을 우회하는 길이 되지 않는다. shadow 에서도 판단은 하고 기록한다.
- Guard 는 허가를 **더하지** 못한다(닫는 쪽으로만). 터지면 enforce 에서 명시적 거부.

### ⑧ Claude Code 그림자

훅 계약(code.claude.com/docs/en/hooks.md, 2026-10-02 확인):

| 훅 | 낼 수 있는 것 | 층 |
|---|---|---|
| SessionStart | additionalContext | 세션 열기 |
| UserPromptSubmit | additionalContext · block | CR: 맥락을 **덧붙인다** |
| PreToolUse | permissionDecision allow · deny · ask · defer · updatedInput | Validate · Arbitrate · Guard |
| PostToolUse | additionalContext · block · updatedToolOutput | Runtime Telemetry → Sensor |
| Stop | decision block | Validate("끝났다" 는 주장) |

- **Shadow**: 훅 실패 → 기록 + 계속. **Enforcement**: 훅 실패 → 명시적 거부.
- 훅은 종료 코드 2 가 아닌 비정상 종료 + JSON 아닌 출력이면 **진행된다**(문서). 그러니 enforce 의 Guard 는 모든 예외를 잡아 deny JSON 을 낸다.
- 문서에 없는 것(시간 초과의 동작 · additionalContext 와 캐시의 관계 · SubagentStop 의 꼴)은 탐침으로 잰다.
