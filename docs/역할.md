# 역할 기록 -- 지금까지 무엇을 누가 맡았고, 각 층이 무엇을 하며 무엇을 못 하는가 (2026-10-02 기준)

이 문서는 **있는 것**만 적는다. 앞으로 지을 것은 [`계획.md`](계획.md) 에 있다.
코드 기준: CR 을 `ms/cr.py` 로 세운 커밋(cr-1) · 시험 102 개 통과 · 의존성 0(표준 라이브러리만).

## 1. 사람의 역할과 에이전트의 역할

| 누가 | 맡은 것 | 이 프로젝트에서 실제로 한 것 |
|---|---|---|
| **사용자** | 무엇을 지을지 · 원칙 · 어느 쪽으로 고칠지의 **결정** | 세 원칙(Telemetry ≠ State · Model 이 뜻을 정함 · LLM 에는 Query 결과만) · 열 원칙(MS 는 provider 가 아니다 …) · A~F 평가 설계 · "짧은 지시문 고쳐라" · "보호 장치를 덜 민감하게" · "캐시를 지키는 배치로" · **층의 경계**(2026-10-02: Policy = decision rule · CR = decision context construction rule · Arbitrate = 선택 · Guard = 허가 · 캐시는 CR 의 책임 · Sensor 는 텔레메트리만 · WALP 는 쓰지 않음 · 순서 ①~⑨) |
| **에이전트(Claude Code)** | 조사 · 설계 · 구현 · 시험 · 측정 · **사실대로 보고** | 선행조사를 코드보다 먼저 커밋 · 사전등록과 "미리 정한 읽기" 를 돌리기 전에 커밋 · 시험이 헛돌지 않는지 코드를 일부러 망가뜨려 확인 · 측정마다 사소한 설명을 재서 가림 |
| **Claude (claude -p)** | 측정 대상 LLM | B · D · F 칸의 제안을 냈다(Sonnet 5.5, CLI 기본). 키가 없어 API 의 Claude · OpenAI · Gemini 는 한 번도 못 불렀다 |
| **모의 provider(sim-*)** | 배선 확인 | 토큰 · 지연을 지어낸다. 증거로 쓰지 않는다 |

## 1-1. 이름을 바로잡는다 -- "Policy" 가 아니라 **Context Runtime(CR)**

지금까지 Context Policy · Prompt Policy(그리고 그 선택기)라고 부른 일은 정책(무엇을 **해도 되나**)이 아니라 **무엇을 LLM 에 보이고
어떻게 말할지를 매 요청 정하는 런타임**이다. 그래서 이름을 **Context Runtime(CR)** 로 고친다(Context Manager 라고도 부를 수 있다).
CR 이 매 요청 내는 결정을 **Context Decision(CD)** 이라 부른다.

| | 지금 | 앞으로 |
|---|---|---|
| CR 의 역할(보일 것 · 말할 꼴 · 지시문 배치 · 결정 기록) | **에이전트가 맡아 MS 코드 안에서** 돌린다(`ms/cr.py`) | CR 이라는 독립 계층으로 옮긴다. MS 는 CR 의 결정(CD)을 받아 쓰기만 한다 |
| "Policy" 라는 이름 | Provider 선택 · 앞으로 Sensor 아래에 설 정책에만 쓴다 | 같음 |

경계를 지키는 까닭은 옮길 때 끊을 자리가 하나여야 해서다: CR 의 입력은 (상태 스냅숏, 요청, 질의 결과), 출력은 CD(최소 맥락 + 정규 프롬프트 +
결정 기록) 하나다. 이 밖의 길로 맥락을 짓는 코드는 두지 않는다.

## 2. 층마다 -- 하는 일 · 못 하는 일 · 붙드는 시험 · 상태

```
USER → MS API → State Query → Context Policy → Prompt Policy → Provider Policy → Provider Adapter → LLM
     → Proposal → Arbiter → Tool → Telemetry → State Manager → (다음 요청의 State)
```

| 층 | 파일 | 하는 일 | **못 하는 일** | 상태 |
|---|---|---|---|---|
| Telemetry | `telemetry.py` · `run_telemetry.py` | "무슨 일이 일어났나" 의 기록. 실행 하나를 정규 꼴(RunRecord: run · tokens · latency · interaction · outcome · cost · decision_ref)로. 결정의 내용은 `decision_record.py`(2026-10-02 뗌). L0 Telemetry 사건도 낸다(`l0.py`, 선택 의존) | 그 자체로 상태가 되기 | 지음 · 시험 |
| State Manager | `manager.py` | 텔레메트리를 모형으로 해석해 그래프에. 모르는 신호 · 범위 밖 · 늦은 관측은 격리 | 모형 없이 상태 만들기 | 지음 · 시험 |
| Model | `model.py` · `usage_model.py` | 신호 → 속성(변환 · 범위 · ttl), 속성 → 파생 상태. `evidence` 창(window · agg · `__n` · `__sum`). 사용 상태 8 개(usage-model-2) | 입력이 없는데 기본값으로 메우기(모르면 모름) · 사건 **하나**로 품질 상태 뒤집기 | 지음 · 시험 |
| State Graph · Query | `graph.py` · `query.py` | 해석된 상태만 산다. 질의가 고른 속성 · 결과 안 관계만 내보낸다 | 그래프 전체를 LLM 쪽으로 | 지음 · 시험 |
| **CR**: Context Decision | `cr.py` · `context.py` · `policy.py`(선택기) | 질의 결과 → 최소 맥락. KEEP · SUMMARIZE · RETRIEVE · DROP · DEFER · COMPRESS. 예산은 실제로 그려진 글자 수 | must 행 빼기 · 행을 조용히 버리기 | 지음 · 시험 · **효과 미확인**(아래 F2) |
| **CR**: 프롬프트 꼴 | `prompt.py` · `policy.py` | 맥락을 어떻게 말할지. 배치 stable_prefix(prompt-text-4): 시스템 글 고정, 계획별 지침은 뒤로, "여기까지 안정" 을 `cache_boundary` 로 **선언**(어떻게 캐시할지는 어댑터) | 도구를 넓히기 · 중재자를 바꾸기 · provider 의 캐시 방식을 알기 · (이 배치에서) 시스템 글 바꾸기 | 지음 · 시험 |
| Provider Policy | `policy.py` | 명시 선택(provider-explicit-1). 상태로 고르는 정책은 인터페이스만 | 승자를 가정하기 | 인터페이스만 |
| Provider Adapter | `providers/` | canonical ↔ OpenAI · Claude · Gemini · claude-cli. 사용량 정규화(OTel), 고유 값은 extensions, 못 하는 옵션은 unsupported. Claude API 는 시스템 글 끝 캐시 지점 | provider 모양을 위로 흘리기 · 옵션 흉내 | 지음 · 녹음 응답으로 시험 · **진짜로 돈 것은 claude-cli 뿐** |
| Proposal | `llm.py` | 글 속 JSON 이든 함수 호출이든 제안일 뿐 | 실행 | 지음 · 시험 |
| Arbiter (옛 이름 WALP Arbiter) | `arbiter.py` | A0~A8 + 예외면 DENY. LLM 이 본 것과 지금 상태를 같이 본다. ⑦ 에서 Validate(A0 · A4) · Arbitrate(선택) · Guard(허가: A6 · A7)로 가른다 | 프롬프트 · LLM 의 말로 허가가 바뀌기 | 지음 · 시험 |
| Tool | `tools.py` · `pipeline.py` | ALLOW 가지 안에서만 불리고, 결과는 텔레메트리로 되돌아간다 | 상태를 직접 쓰기 | 지음 · 시험 |
| MS API · Request Manager | `runtime.py` | 상태 → 정책 셋 → 루프 → DecisionRecord + RunRecord → 상태. `replay(결정 기록)` 로 정책 결정 재현 | 원 측정을 정책에 넘기기(정책은 파생 상태만 본다) | 지음 · 시험 |
| 평가 | `eval.py` | A~F · 과업 7 · 섞은 순서 · `--fresh` · 부트스트랩 구간 · 품질 비열등 · 안전 | provider 사이 비교 | 지음 · claude-cli 로 B·D·F 만 |

이웃 저장소와의 관계(아직 **안 이었다**):

| 저장소 | 이미 있는 것 | MS 에서 보면 |
|---|---|---|
| `Sensor`(llmsensor) | 센서 다섯 → Reading(OK · SUSPECT · FAULT · UNKNOWN) → 성능모형 잔차 → 증거 융합 Q → **Verifier**(ACCEPT · REJECT · RETRY · DEGRADE + 정책 제안: token_budget · retry_limit · terminate_on_repeat · route). Claude Code 세션 JSONL 을 바로 읽는다 | Reading · Q · 잔차는 **텔레메트리**로만 받는다(MS 원칙 1). Verifier 의 판정 · 정책 제안은 **배선하지 않는다** -- Sensor 가 이미 판단한 것이라 받으면 Sensor 와 Policy 가 섞인다(2026-10-02 고침: 앞서 "Verifier 를 validate 로 쓴다" 고 적었던 것은 틀렸다) |
| `walp` | -- | **쓰지 않는다**(2026-10-02 결정). 코드 · 지시문 · 텔레메트리 칸에서 WALP 를 뺐다 |

## 4. 이 저장소의 일하는 방식(지금까지 지킨 것)

1. 선행조사(`paper/선행조사/`)를 코드보다 먼저 커밋한다.
2. 측정 전에 사전등록 또는 "미리 정한 읽기" 를 커밋한다(`eval/PREREG_*.md`). 결과는 그 아래에 덧붙인다.
3. 수를 말하기 전에 사소한 설명을 재서 가린다 -- X1~X3 이 그렇게 잡혔다.
4. 시험을 지으면 코드를 일부러 망가뜨려 빨개지는지 본다(지금까지 25 가지 이상).
5. 모의 결과는 증거가 아니라고 보고서 머리에 적는다. claude-cli 는 사전등록 칸이 아니라 따로 적는다.
