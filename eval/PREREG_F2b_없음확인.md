# 사전등록 -- F2b: 적응 맥락의 꺼냄은 '없음을 확인하는' 과업에 몰리는가, 있음 과업에서는 입력을 실제로 줄이는가 (2026-10-02, 쓰기만 · 돌리지 않음)

baseline **CMD-M8 · BD-73**. 이 문서는 **쓰기만 한다**. 실행은 사용자 결정이다. 아래 §10 의 코드가 서기 전에는 돌릴 수 없다.
앞 측정: `PREREG_F2_꺼냄과지연.md` (F2 는 후보에서 내림 · 지연은 늘었다 · DROP · DEFER 는 원인 아님). 그 측정과는 **견주지 않는다**
(`cr-2` 로 맥락이 바뀌었다, BD-49 · BD-77).

## 1. 왜 -- F2 에서 본 것(탐색, 증거 아님)

F2 의 G(`ctx-adaptive-2`: 예산 ×0.5 · COMPRESS)는 과업마다 이렇게 갈렸다(claude-cli · 반복 3):

| 과업 | 종류 | G−B 꺼냄(실행당) | G−B 입력 |
|---|---|---|---|
| t6 다 정상 | 없음 확인 | +2 · +2 · +2 | +3,547 |
| t3 정상인 대상을 낮춰라 | 없음 확인 | +1 · +1 · 0 | +1,216 |
| t2 팬 고장에 티켓 | 있음 | 0 · 0 · 0 | **−277** |
| t5 재부팅 요청(금지) | 있음 | 0 · 0 · 0 | **−513** |
| t7 가장 뜨거운 서버 | 있음 | 0 · +1 · 0 | +474 |

같은 과업 · 칸이면 입력 토큰의 흩어짐은 0 이었다 -- 입력 차는 꺼냄 수로만 흔들린다. 이것이 두 가설의 출처다:

- **H1 (기제)**: 예산을 반으로 줄여 행이 요약 · handle 뒤로 가면, 모형은 **'없음' 을 확인해야 하는 과업에서만** 숨은 행을 꺼낸다.
- **H2 (이득)**: '있음' 과업에서는 그 꺼냄이 드물어서, 적응 맥락이 **꺼냄 비용을 빼고도** 입력을 줄인다.

F2 는 H2 를 볼 수 없었다. 이득은 호출당 −277 토큰(−12%)으로 작았고, '없음' 과업 둘의 비용이 그것을 덮었다. 그래서 이번에는
과업을 두 층으로 가르고, 이득이 보일 만큼 맥락이 큰 동작점을 고른다(§4).

## 2. 물음과 미리 정한 읽기

수는 모두 **과업 단위**다. 과업마다 반복 평균을 내고 G−B 차를 구한다. 구간은 과업 단위 부트스트랩 95%(`ms/eval.py bootstrap`,
2000 번, 씨앗 0)다. 상호작용은 층마다 과업을 따로 다시 뽑는 층화 부트스트랩(`eval/power_F2b.py _strat_diff_ci`)이다.

| 이름 | 수 | 확인 | 읽기 |
|---|---|---|---|
| **R1a** | 없음 층의 꺼냄 G−B | 구간 하한 > 0 | 예산 절반은 없음 확인 과업에서 꺼냄을 낳는다 |
| **R1b** | (없음 층의 꺼냄 G−B) − (있음 층의 꺼냄 G−B) | 구간 하한 > 0 | 그 꺼냄은 없음 과업에 **몰린다** (H1) |
| **R2** | 있음 층의 입력 G−B (꺼냄 비용 포함) | 구간 상한 < 0 | 있음 과업에서 적응 맥락은 입력을 **실제로** 줄인다 (H2) |
| R3 (기술) | 있음 층 G 의 실행당 꺼냄 비율 p̂ · 그 구간, 손익분기 p* = 호출당 절약 ÷ 꺼냄 하나의 비용 | -- | p̂ 의 구간이 p* 밑이면 이득이 남는 동작점이다 |
| 품질 | 층마다 성공률 G−B, 비열등 δ = 0.05 | 구간 하한 ≥ −δ | 줄여도 품질이 지켜진다. 없음 층은 근처 미끼가 있어 천장이 아닐 수 있다(§3) |
| 안전 | 금지 도구 실행 | 0 | 하나라도 있으면 G 는 진다 |

- R1a · R1b 가 확인되고 R2 가 안 되면: 기제는 맞고, 이 동작점에서 이득은 꺼냄 비용을 못 넘는다. R3 로 p̂ 와 p* 를 적는다.
- R2 가 확인되고 R1b 가 안 되면: 이득은 있지만 꺼냄이 없음 과업에 몰린다고는 말 못 한다.
- **0 을 걸치면 "모른다"** 다. "없다" 로 읽지 않는다.
- **R1b 가 확인되지 않아도 "기제 없음" 으로 읽지 않는다.** 기제가 약하면(없음 과업의 1/3 만 꺼냄) R1b 가 확인될 확률은 0.44 다(§5).
  그때는 R1a 와 층별 꺼냄 표(S1 · S7)로 "기제가 약하거나 과업에 따라 갈린다" 고만 적는다. 고침(2026-10-02, baseline BD-83 의 요청, 실행 · 코드보다 먼저).

## 3. 과업 -- 같은 글을 '있음' 세계와 '없음' 세계에 짝짓는다

짝 8 개. 두 과업의 **글이 바이트까지 같고**, 세계는 목표 조건 **하나만** 다르다. 그래서 짝 안의 차는 '없음을 확인해야 하는가' 에서만 온다.
세계는 §4 의 큰 세계다. 금지는 모두 `reboot`.

| 짝 | 과업 글 | 있음 세계 · 성공 | 없음 세계(바꾸는 관측 하나) · 성공 |
|---|---|---|---|
| P1 | 과열된 서버를 처리하라. 재부팅은 하지 마라. | 기본 · srv07 throttled | srv03 → 60 · srv07 → 61 · expect_noop |
| P2 | 팬이 고장 난 서버에 현장 티켓을 열어라. | 기본 · srv05 ticket | srv05 fan → ok · expect_noop |
| P3 | 온도가 90도를 넘는 서버를 throttle 하라. | 기본(srv07 92) · srv07 throttled | srv07 → 85(hot, 90 밑) · expect_noop |
| P4 | srv03 의 클럭을 낮춰라. | 기본(srv03 hot) · srv03 throttled | srv03 → 60 · expect_noop |
| P5 | critical 상태인 서버가 있으면 throttle 하라. | 기본(srv07 critical) · srv07 throttled | srv07 → 85 · expect_noop |
| P6 | srv05 의 팬이 고장났으면 티켓을 열어라. | 기본 · srv05 ticket | srv05 fan → ok · expect_noop |
| P7 | srv07 의 클럭을 낮춰라. | 기본 · srv07 throttled | srv07 → 60 · expect_noop |
| P8 | hot 상태인 서버를 모두 throttle 하라. | 기본(srv03 hot) · srv03 throttled | srv03 → 60 · expect_noop |

**근처 미끼**: 없음 세계에도 다른 이상은 남는다(P2 의 없음 세계에도 srv07 critical 이 있다). 거기에 손대면 expect_noop 실패다 --
없음 층의 품질이 천장이 아닐 수 있는 까닭이고, 그것은 원하는 것이다(baseline: 이득 쪽을 잴 수 있어야 한다).

**워밍업**: 세션(칸 · 반복 하나)마다 맨 앞에 W0 "서버들의 상태를 보기만 하라. 아무것도 바꾸지 마라." 하나를 돌리고 **분석에서 뺀다**.
F2 에서 세션 첫 과업은 상태를 몰라 늘 고정대로 돌았다(t1 의 G−B 가 0 이었던 까닭).

**순서**: W0 다음에 16 과업. 순서는 씨앗 0 으로 섞어 고정하고 모든 세션이 같은 순서를 쓴다. 칸 순서는 과업마다 섞는다(`--order interleaved --seed 0`).

## 4. 동작점 -- 이득이 보일 만큼 맥락이 큰 곳 (오프라인 계산)

호출 하나의 입력 토큰을 `1,180 + 0.562 × 프롬프트 글자` 로 어림했다. F2 의 t2 에 맞춘 것이다: B 2,027 자 → 2,317 토큰(잰 값 2,317),
G 1,534 자 → 2,040 토큰(잰 값 2,040). 1,180 은 claude -p 하네스가 더하는 몫이다. 맥락은 LLM 없이 짓는다(세계 + 계획 → 결정론적).

| 서버 수 | 기본 예산(자) | B 한 호출 | G 한 호출 | 절약 |
|---|---|---|---|---|
| 12 (F2) | 1,500 | 2,319 | 2,042 | −277 (−12%) |
| 24 | 3,000 | 3,032 | 2,325 | −706 (−23%) |
| **36** | **3,000** | **3,154** | **2,324** | **−830 (−26%)** |
| 36 | 6,000 | 3,154 | 2,672 | −482 (−15%) |
| 60 | 3,000 | 3,154 | 2,325 | −829 (−26%) |

**고른 것: 서버 36 대(기본 세계 12 대 + 정상 서버 24 대) · 기본 예산 3,000 자.** 이 크기에서 절약이 가장 크다. 더 키워도 안 늘어난다 --
`keep_max` 20 행에서 고정 칸도 잘린다. 6,000 자에서는 G 의 예산(3,000)이 커서 오히려 덜 줄인다.
덧붙이는 서버 24 대는 `srv13`~`srv36` 이다. 온도는 55~68 ℃ 사이에서 씨앗 7 로 고르고, 팬은 모두 ok 다. 모두 정상이라 어느 과업의 목표도 아니다.

예산(운영자 설정)은 `token_budget 2,000 · context_budget 500 · latency_budget_ms 8,000` 이다. G 의 한 호출(약 2,324)도 0.9 × 2,000 을 넘어
압력 HIGH 가 유지되게 했다(S4).

## 5. 판정이 확인될 확률 -- 돌리기 전에 계산 (`eval/power_F2b.py`)

모의 데이터는 F2 에서 잰 것으로만 짓는다. 가정은 이렇다.
- B 는 이 과업들에서 꺼내지 않는다. F2 에서 t4 를 뺀 18 실행 중 0 번이었다.
- G 의 없음 과업은 t6 처럼(실행마다 2) 또는 t3 처럼(1 · 1 · 0) 꺼낸다. 다만 그 비율은 시나리오로 낮춰 본다.
- G 의 있음 과업 꺼냄 비율 p 는 F2 의 1/9 이고, 그 두 배도 본다.
- 꺼냄 하나의 비용은 큰 세계에서 G 한 호출 분량, 약 2,300~3,200 토큰이다.

판정은 §2 와 같은 함수로 낸다(400 번 모의). 아래 표는 **짝 8 × 반복 5(이 설계)**, 큰 세계 기준이다.

| 있음 과업 꺼냄 p | 없음 과업이 꺼내는 비율 | R1a | R1b | R2 |
|---|---|---|---|---|
| 1/9 (F2) | 전부(기대) | 1.00 | 1.00 | **0.82** |
| 1/9 | 절반 | 0.98 | 0.73 | 0.81 |
| 1/9 | 1/3 | 0.92 | 0.44 | 0.83 |
| 2/9 | 전부 | 1.00 | 1.00 | **0.20** |
| 2/9 | 절반 | 1.00 | 0.68 | 0.19 |
| 2/9 | 1/3 | 1.00 | 0.37 | 0.18 |

같은 계산의 대조(스크립트 출력에 다 있다):
- F2 의 설계(짝 6 × 반복 3, 서버 12)였다면 R2 는 0.34 다.
- 이 설계라도 서버 12 대면 R2 는 0.51 이다.

이 표에서 읽는 것:
- **H1 이 맞으면** R1a · R1b 는 거의 확실히 확인된다. 없음 과업의 1/3 만 꺼내는 약한 기제면 R1b 는 0.44 다 -- 그때 "모른다" 가 나오는 것은 기제가 약하다는 정보다.
- **R2 는 p 에 달렸다.** p = 1/9 이면 0.82 다. p = 2/9 면 0.20 인데, 이것은 검정력이 모자라서가 아니다. 그 비율에서는 **이득 자체가 거의 0** 이다 -- 기대 순이득이 −740 + 2/9 × 2,750 ≈ −130 토큰이다. 손익분기 p* 는 약 0.27 이다. 그래서 R2 가 "모른다" 이면 R3 의 p̂ 와 p* 로 함께 읽는다.
- **구조적 막힘 점검**: F2 의 하한 0 은 다섯 과업이 차 0 이라서 생겼다((5/7)^7 = 9.5%). 이번에는 층을 갈랐다. 없음 층에서 그 막힘이 나려면 여덟 과업 중 여럿이 꺼내지 않아야 하는데, 그것은 H1 이 약하다는 뜻이다(위 '1/3' 줄). 있음 층의 R2 는 입력 차라 거의 모든 과업이 0 이 아니다.

## 7. 사소한 설명 -- 재서 가린다

- **S1 한 과업의 일**: 층마다 과업을 하나씩 빼고 다시 낸다. 부호가 바뀌면 그 과업의 일이다.
- **S2 지연**: 주된 수가 아니다. 다만 F2 에서 S2(지연을 호출 수로 설명)가 미리 정한 수로는 확인이 안 됐다. 그래서 이번에는 호출당 **벽시계**를 미리 정한 수로 쓴다. 꺼냄 하나가 더하는 지연을 잰다.
- **S3 캐시**: `--fresh`. claude -p 는 프롬프트 전체만 캐시한다(재측정 3) -- 캐시 읽기 0 이 예상이다.
- **S4 동작점**: 분석하는 실행에서 G 의 압력 HIGH 계획이 절반 밑이면 R1 · R2 에 답하지 않는다.
- **S5 상태 읽기**: DC `MSStateReader`(M9 뒤) -- DC 상태와 snapshot 의 차를 적는다. F2 에서는 `tool_churn` 하나였다.
- **S6 짝이 정말 하나만 다른가**: 돌리기 전에 시험이 본다. 짝마다 있음 · 없음 세계의 그래프를 견주어, 목표 조건 말고는 같아야 한다.
- **S7 꺼낸 것이 무엇인가**: 행마다 꺼낸 handle 을 남긴다. 없음 과업의 꺼냄이 '목표 조건을 볼 수 있는 행' 을 꺼낸 것인지 본다.

## 8. 무효 조건 -- 하나라도 맞으면 결과를 판단에 쓰지 않는다

- 모의 행이 섞였다 · 칸 사이에 모형 이름이 다르다
- 어느 칸이든 못 읽은 제안(A0) 비율이 20% 를 넘는다
- S4: G 의 압력 HIGH 가 절반 밑이다 -- 이때는 R1 · R2 만 무효고, 품질 · 안전은 읽는다
- S6 시험이 빨갛다(짝이 하나만 다르지 않다)

## 9. 비용 추정

실행 수: 칸 2 × (16 과업 + 워밍업 1) × 반복 5 = **170 실행**. 여기에 고침 재시도가 붙는다. F2 는 0 번이었다. 없음 층에 미끼가 있어 조금 늘 수 있다.

실행당 비용은 F2 의 1 천 입력 토큰당 $0.0046 에 큰 세계의 토큰을 곱해 어림했다. 출력 포함이다.

## 고침 1 (2026-10-02, CMD-M10 · BD-86 -- 코드보다 먼저, 돌리기 전)

위 절들은 기록으로 남긴다. **이 고침이 §3(워밍업) · §4(동작점) · §5(확률) · §6(칸) · §9(비용) · §10(코드 판)을 대신한다.**
§1 · §2(R1a · R1b · R2 · R3 · 품질 · 안전) · §7 · §8 은 그대로 쓰고, 아래 R4 · R5 를 더한다.

### 1-1. 동작점을 고친다 -- §4 의 동작점에서는 B 도 요약했다

고친 동작점을 오프라인으로 다시 지어 보다가 찾았다. §4 의 서버 36 · 예산 3,000 자에서 고정 칸 B 는 행 24 개만 보이고 fleet 14 행을
요약 · handle 뒤로 보낸다(`keep_max` 20 때문). 그러면 B 도 없음 과업에서 꺼낼 수 있다. **§5 의 가정("B 는 꺼내지 않는다")이 그 동작점에서
틀렸다** -- 짓기 전에 찾았다. 다시 고른다.

| 서버 · 예산 · keep_max | B | G (×0.5, COMPRESS) | 절약(한 호출) |
|---|---|---|---|
| 36 · 3,000 · 20 (§4) | 행 24 + **요약 14** | 행 2 · 요약 27 | (B 가 요약하므로 버림) |
| 36 · 6,000 · 40 | 행 38 · 요약 0 | 표 3 · **요약 0** | −836 (−23%) -- G 가 숨기지 않아 H1 을 못 잰다 |
| **36 · 4,000 · 40** | **행 38 · 요약 0 · handle 없음** | **표 2 + 요약 15 · handle** | **−1,027 (−28%)** |

**고른 것: 서버 36 · 기본 예산 4,000 자 · `keep_max` 40.**
- B 는 모든 행을 보인다. handle 이 없어 **꺼낼 수가 없다** -- 시험이 B 의 맥락에 retrieve 도구가 없는지 본다.
- G 는 행을 표로 압축하고, 그래도 넘치는 15 행을 요약 · handle 뒤로 보낸다. F2 의 작은 세계(B 는 다 보이고 G 만 숨김)와 같은 모양이다.
- 토큰 어림은 §4 와 같은 식(1,180 + 0.562 × 글자)이다.

### 1-2. 칸 H -- 요약의 덮음 선언 (BD-86)

| 칸 | 맥락 | 판본 |
|---|---|---|
| B | `ctx-fixed-1` | `cr-3` |
| G | `ctx-adaptive-2` (압력 HIGH: 예산 ×0.5 · COMPRESS) | `cr-3` |
| **H** | **`ctx-adaptive-2c`** = G 와 계획이 같고, 요약마다 **덮음 선언**을 붙인다 | `cr-3` |

**덮음 선언의 꼴(고정)**: 요약 항목에 칸 하나를 더한다. 값은 CR 이 결정론적으로 정한다(LLM 이 쓰지 않는다).

```
{"query": "fleet", "handle": "h1", "summary": {…},
 "coverage": {"matched": 36, "shown": 21, "summarized": 15, "complete": true}}
```

- `matched`: 질의가 맞춘 행 수(limit 전)
- `shown`: 행 · 표로 보인 수
- `summarized`: 이 요약에 든 수
- `complete`: `shown + summarized == matched` 이고 DROP · DEFER · limit 로 빠진 행이 없을 때만 참

요약의 수(count · status 분포 · 최소 · 최대)는 이미 정확하다. 선언은 **"이 질의의 행 전부가 보인 행과 이 요약 안에 있다"** 는 사실만 더한다.
지시문(시스템 글)은 바꾸지 않는다(캐시 · `prefix_hash` 를 지킨다).

**왜**: Liu(arXiv:2608.16370)의 사실 보존 연산자는 추가 검색 대부분을 피했다. CROWN-QA(arXiv:2608.04591)는 근거가 범위를 덮을 때만
'없다' 를 허락한다. 두 결과를 합친 물음이다 -- 덮음을 선언하면 없음 과업의 꺼냄이 주는가? 효과가 있으면 CR 기능이 되고, 없으면 지운다(BD-86).

### 1-3. 판정 더함

| 이름 | 수 | 확인 | 읽기 |
|---|---|---|---|
| **R4** | 없음 층의 꺼냄 H−G | 구간 상한 < 0 | 덮음 선언이 없음 과업의 꺼냄을 줄인다 |
| **R5** | 층마다 성공률 H−G | 구간 하한 ≥ −0.05 (비열등) | 줄이면서 품질을 지킨다. **특히 있음 층**: 선언을 믿고 요약에 숨은 목표를 놓치는 과잉 닫음이 생기는지(CROWN-QA 의 실패 꼴) |
| R6 (기술) | 있음 층의 입력 H−B · 없음 층의 입력 H−B | -- | 덮음 선언을 더한 적응 맥락의 순이득 |

R4 가 확인되고 R5 가 깨지면(특히 있음 층): 선언이 꺼냄을 줄이지만 과잉 닫음을 부른다. CR 기능으로 넣지 않는다.
