# 사전등록 -- 상태 기반 적응 정책 (2026-10-01, 수를 보기 전)

이 문서는 **어떤 수도 나오기 전에** 커밋한다. 이 문서를 고친 뒤에 나온 결과는 이 사전등록의 결과가 아니다.

## 가설

> H. 텔레메트리에서 모형이 해석한 상태로 Context Policy 와 Prompt Policy 를 고르면(적응), 같은 provider 에서 고정 정책과 견줘
> **품질을 지키면서** 입력 토큰 · 지연 · 재시도 · 비용을 줄인다.

나눠서 판정한다 -- 셋이 같은 방향이라고 가정하지 않는다(arXiv:2609.32961 조각: 토큰 1/3 인 정책이 20~80% 더 느렸다).

| | 비교 | 무엇이 줄었나 |
|---|---|---|
| H1 | A↔C · B↔D (적응 맥락, 고정 프롬프트) | 과업당 입력 토큰 |
| H2 | A↔C · B↔D | 과업당 종단 지연(`total_ms`) |
| H3 | C↔E · D↔F (적응 프롬프트를 더함) | 과업당 총 토큰 · 재시도 |
| H4 | 모든 짝 | 비용(가격표가 있을 때만. 없으면 판정 안 함) |

## 칸

| 칸 | provider | Context Policy | Prompt Policy |
|---|---|---|---|
| A | OpenAI | fixed | fixed |
| B | Claude | fixed | fixed |
| C | OpenAI | adaptive | fixed |
| D | Claude | adaptive | fixed |
| E | OpenAI | adaptive | adaptive |
| F | Claude | adaptive | adaptive |

**provider 사이(A↔B 등)는 비교하지 않는다.** 이 설계는 provider 의 승자를 가리려는 것이 아니다. provider 는 칸 안에서만 고정된다.

## 같게 하는 것

- 같은 과업 모음(`eval/tasks/*.json`), 같은 순서, 같은 성공 기준(과업 파일의 `success` -- 최종 **상태 그래프**에 대한 술어 + `forbidden`
  도구가 실행되지 않음). 성공은 LLM 이 판정하지 않는다.
- 같은 WALP 허가(grants). 같은 `max_rounds`.
- 한 칸의 과업들은 **한 세션**으로 차례로 돈다 -- 적응 정책은 앞 과업들의 텔레메트리에서 나온 상태를 본다. 고정 정책은 그 상태를 안 본다.
- 칸마다 반복 `n` 번(기본 3). 순서는 과업 파일 순서 그대로.

## 품질 · 안전 -- 단단한 제약 (줄인 것을 셈하기 전에 먼저 본다)

1. **안전**: `forbidden` 도구가 한 번이라도 실행되면 그 칸은 **실격**이다. 줄인 것과 무관하다.
2. **품질 비열등**: 적응 칸의 성공률이 짝 고정 칸보다 **5%p 넘게** 낮으면 그 칸은 실격이다(비열등 한계 δ = 0.05).
   과업 수가 적어 신뢰구간이 넓으면 "판정 불가" 다 -- 실격이 아니라고 통과로 읽지 않는다.
3. 위를 지난 칸에서만 H1~H4 를 본다.

## 판정

- 칸 짝마다 과업당 평균 차와 **부트스트랩 95% 구간**(과업 단위 재표집 2000 번, 씨앗 고정)을 낸다.
- 구간이 0 을 넘어 줄었으면 "줄었다", 0 을 넘어 늘었으면 "늘었다", 걸치면 "모른다".
- **H 지지** = 품질 · 안전을 지나고, H1 이 두 provider 모두에서 "줄었다". H2 · H3 · H4 는 따로 적는다.
- 한 provider 에서만 줄었으면 "그 provider 에서만" 이라고 적는다. 일반화하지 않는다.

## 사소한 설명 -- 미리 적고 잰다

| 시시한 설명 | 어떻게 죽이나 |
|---|---|
| 적응 칸이 적은 토큰을 쓴 것은 상태가 아니라 **그냥 예산이 작아서**다 | 고정 칸의 예산 = 적응 칸이 상태 LOW 일 때의 예산. 적응이 줄이는 것은 상태가 HIGH 일 때뿐이어야 한다 -- 상태별 칸 나눔을 같이 보고한다 |
| 세션 처음에는 상태가 **모름**이라 적응이 고정과 같다 | 상태가 정해진 과업과 모름인 과업을 나눠 보고한다 |
| 토큰이 줄어든 것은 실패해서 일찍 끝났기 때문이다 | 토큰 · 지연은 **성공한 과업만**으로도 따로 낸다 |
| provider 의 캐시가 뒤 과업을 싸게 만들었다 | `cached_input_tokens` 를 따로 내고, 캐시를 뺀 입력으로도 비교한다 |
| 지연 차는 네트워크 흔들림이다 | 지연은 중앙값과 구간으로만 말한다. 구간이 0 을 걸치면 "모른다" |

## 같지 않은 것 -- 같다고 가정하지 않는다

보고서 머리에 provider 별 능력 표(`capabilities`)를 그대로 붙인다: JSON 스키마 강제가 native 인지 prompt 인지, 추론 조절이
되는지, TTFT 가 있는지, 캐시 토큰을 보고하는지. Prompt Policy 가 고른 옵션 중 provider 가 못 하는 것은 **무시되고 기록된다**
(`unsupported`) -- 흉내 내지 않는다.

## 이 사전등록이 아닌 것

- `simulated` provider 로 돈 결과(배선 확인)는 이 가설의 증거가 아니다. 보고서가 그것을 머리에 크게 적는다.
- `claude-cli` provider(`claude -p`)는 Claude Code 하네스의 시스템 프롬프트가 붙는다 -- API 의 Claude 와 **같지 않다.**
  그 결과는 B · D · F 칸이 아니라 따로 적는다.

## 고침 1 (2026-10-01, 진짜 API 수가 하나도 나오기 전)

claude-cli 배선 측정 둘(사전등록 밖)에서 본 두 가지 때문에 설계를 고친다. 가설 · 칸 · 판정 규칙은 그대로다.

1. **순서**: 칸을 통째로 차례로 돌지 않는다. 반복마다 · 과업마다 칸 순서를 씨앗 고정 난수로 섞는다(`--order interleaved --seed 0`).
   재측정에서 앞 측정이 쓴 provider 캐시를 B · D 만 읽어 비용이 4 배 갈렸다.
2. **캐시 안 된 입력**(`input_tokens − cached_input_tokens`)을 지표에 더한다. 같은 지시문을 쓰는 칸끼리는 섞어도 캐시를 나눠 쓰므로
   H1(입력 토큰)은 **두 가지로 다 본다.** 둘이 갈리면 "캐시 때문에 갈린다" 고 적고 H1 을 판정하지 않는다. H4(비용)도 같다.
3. **사용 모형 usage-model-2**: answer_reliability LOW · correction_rate HIGH 는 표본 3 개 이상 · 사건 2 번 이상일 때만.
   (usage-model-1 은 창 안의 실패 한 번이 곧 LOW 였다.) 진짜 측정은 usage-model-2 로 한다.
