# 선행조사 -- ② Sensor → Telemetry 배선 (2026-10-02)

코드보다 먼저 커밋한다. 짓는 것은 계획(`docs/계획.md`)의 ② 하나다: **Sensor(llmsensor) 의 출력을 MS 의 텔레메트리로 받는 계약**.
DC · CR · Policy 로 가는 것(③ 이후)은 이 문서의 범위가 아니다.

**이 조사는 얕다.** 아래 인용은 전부 검색 조각만 보고 단 것이다(`[출처:조각]`). 전문을 읽은 것은 없다.
Sensor 의 출력 꼴만은 코드를 직접 읽었다(`llmsensor/pipeline.py` · `trace.py` · `residual.py` · `fusion.py`, 커밋 d4b80b3).

## 1. Sensor 가 실제로 내는 것 -- 측정인가 결정인가

`llmsensor.sense(task) -> {cls, telemetry, readings, residual, fusion, verdict}`

| 칸 | 무엇 | 가르기 | 배선 |
|---|---|---|---|
| `telemetry` | T(토큰) · T_out · turns · L(도구 호출) · E(실패) · R(재시도) · latency · missing_results | **측정** | 한다 |
| `readings` | 센서 다섯(execution · constraint · consistency · behavior · outcome): status(OK · SUSPECT · FAULT · UNKNOWN) · value · why · detail | **관측**(검출기의 출력) | 한다 |
| `residual` | 성능모형 대비 r_T · z_T · r_R · r_E · R_sys(순위 점수) | **유도된 측정** | 한다 |
| `fusion` | Q = 판독의 로그 우도비 합(+사전) · calibrated · evidence | **추정**(행동 결정은 아니다) | **안 한다**(아래 열린 결정 1) |
| `verdict` | ACCEPT · REJECT · RETRY · DEGRADE + 정책 제안(token_budget · retry_limit · terminate_on_repeat · route) | **결정** | **안 한다** -- 받으면 Sensor 와 Policy 가 섞인다 |

Q 를 안 받는 까닭 둘: (1) Q 는 판독의 **함수**다(`fusion.py: lo += log(LR[sensor][status])`). 판독과 Q 를 둘 다 받으면 같은 증거를 두 번 센다.
(2) 증거를 묶어 뜻을 정하는 것은 MS 원칙 2(State 의 뜻은 Model 이 정한다)의 자리다.

## 2. 가장 가까운 선행연구

| 우리 것 | 가장 가까운 것 | 확인수준 | 겹치는 것 · 다른 것 |
|---|---|---|---|
| **전체 고리** Sensor → DC → Policy/CR → Validate/Arbitrate/Guard → Executor | **MAPE-K**(Monitor · Analyze · Plan · Execute over Knowledge) -- Kephart & Chess, *The Vision of Autonomic Computing*, IEEE Computer 2003. 자가적응 시스템의 대표 참조 모형 | [출처:조각] | **우리 구조는 MAPE-K 다.** Sensor·Telemetry = Monitor, Model·DC = Analyze, CR·Policy = Plan, Validate·Arbitrate·Guard·Executor = Execute, State Graph = Knowledge. 새 구조라고 말하지 않는다 |
| LLM 이 제안하고 결정론적 핵심이 집행 | **ASPO** -- *Self-Adaptive Multi-Agent LLM-Based Security Pattern Selection for IoT Systems* (arXiv:2605.00741, 2026-05) | [출처:조각] | **아래 절반(⑥~⑦)과 거의 같다.** LLM 에이전트가 완화 조합을 제안, 결정론적 최적화 핵심이 닫힌 세계 행동 무결성 · 충돌 없는 조합 · 자원 타당성을 매 결정마다 집행, MAPE-K 안에서. 조각: 안전 불변식 100%, 꼬리 지연 · 에너지 21~23% 감소. 다른 것: IoT 보안 도메인 · LLM 쓰임새 비용(토큰 · 캐시 · 맥락)을 상태로 안 다룬다(조각 기준) |
| 에이전트 개선에 MAPE 고리 | *Adaptive Data Flywheel: Applying MAPE Control Loops to AI Agent Improvement* (arXiv:2510.27051, EACL 2026 industry, NVIDIA NVInfo) | [출처:조각] | 사람 피드백 → 실패 유형(라우팅 5.25% · 질의 바꿔 쓰기 3.2%) → **미세조정**. 우리 고리는 매 요청의 런타임 결정이고 가중치를 안 바꾼다 |
| **판독을 텔레메트리 꼴로** | OpenTelemetry GenAI **`gen_ai.evaluation.result`** 이벤트(semconv v1.39~, Development 안정도): `gen_ai.evaluation.name` · `score.value` · `score.label`(낮은 기수) · `explanation` | [출처:조각] | **Reading 과 거의 1:1** -- name=센서, score.label=OK·SUSPECT·FAULT·UNKNOWN, score.value=value, explanation=why. 품질 판단을 "결정" 이 아니라 **관측 이벤트**로 다루는 표준이 이미 있다. 평가 결과에 검증 가능한 증거 참조를 붙일지는 논의 중(eunomia.dev 2026-08) |
| 텔레메트리를 맥락 결정으로 되먹임 | **VISTA** -- *LLM Agents Are Latent Context Managers: Eliciting Self-Managed Context via State Proprioception* (arXiv:2606.30005) | [출처:조각] | 블록별 토큰 · 최근성 · 접근 이력을 **LLM 에게 대시보드로 보여** LLM 이 맥락을 스스로 관리. 우리는 반대로 **결정론적 CR** 이 텔레메트리(→ DC)를 보고 정한다. ④ 에서 "LLM 에게 맥락 상태를 보이는 것" 을 CR 의 선택지로 둘지 다시 본다 |
| 관측 도구의 되먹임 | LangSmith(online evals · automation rules) · Langfuse(scores) | [출처:조각] | 실시간 점수 → 사람 검토 · 데이터셋 · 웹훅으로 **보낸다**(개선 고리). 조각에서는 그 점수가 **같은 요청의 맥락 결정**으로 돌아가는 것을 못 봤다 |
| 감지와 결정의 분리 | 로보틱스 3층(3T) · 감지 → 융합 → 세계 모형 → 계획 | [출처:조각] | 융합(추정기)은 **감지 쪽**, 계획이 결정. 그러니 Q 를 "결정" 이라 부르는 것은 틀리다 -- 그래도 안 받는 까닭은 위 1 절(이중 계산 · 원칙 2) |

④(DC → CR) 때 볼 것으로 함께 걸린 것: *TokenPilot: Cache-Efficient Context Management for LLM Agents* (arXiv:2606.17016) ·
*Context as an Environment: Programmatic Context Management for Long-Horizon Agents* (arXiv:2608.21690). [출처:조각] -- 제목만 봤다.

## 3. 설계에 주는 것 (② 의 계약안)

1. **MS 는 Sensor 를 import 하지 않아도 된다.** 계약은 `sense()` 출력의 **데이터 꼴**(dict / JSONL)이다. `ms/sensing.py` 는 그 dict 를 받아
   텔레메트리 신호로 편다. llmsensor 를 설치하면 편하게 부를 수 있을 뿐(선택 의존).
2. 받는 칸은 `telemetry` · `readings` · `residual` 셋. **`fusion` · `verdict` 칸이 들어오면 버리고 격리함에 남긴다**(조용히 쓰지 않는다).
3. 판독 한 개 = OTel `gen_ai.evaluation.result` 꼴의 신호 하나: `sensor.<이름>` 에 label(status) · value · explanation(why). 
   신호 이름 공간은 MS 의 것(`sensor.*`)이고, MS 모형이 그 뜻을 정한다(③).
4. **판독의 `why` · `detail` 에는 날글이 섞인다 -- 코드로 확인했다(llmsensor d4b80b3).**

   | 센서 | 날글이 드는 곳 |
   |---|---|
   | outcome | `detail.tail` = 명령 stdout · stderr 의 **마지막 400 자** · `why` 에 명령줄 · 검증 함수 예외 메시지 |
   | execution | `detail.unresolved` · `written_but_missing` = 겨냥(명령 이름) · **파일 경로** |
   | constraint | `detail.violations` · `why` = 스키마 위반 메시지(답의 **값**을 `{v!r}` 로 인용) |
   | behavior · consistency | 수 · 참거짓만(`z` · `value` · `claim` · `verifications` · `numbers` …) |

   그래서 계약은 **수만 받는다**: `status` · `value`(수) · 센서마다 정한 **수 칸 화이트리스트**(목록 칸은 길이만). `why` 와 날글 칸은 버린다.
   (출력 꼬리에는 비밀이 섞일 수 있다 -- MS 의 상태 · 격리함 · 원장 어디에도 남기지 않는다.)
5. UNKNOWN 은 신호로 들어오되 값이 "모름" 이다 -- 모형이 OK 로 세지 않게(③ 의 시험).

## 아직 못 지운 가능성

- **ASPO 의 전문을 안 읽었다.** 그들이 이미 "모니터 신호 → 상태 → LLM 제안 → 결정론적 집행" 을 우리와 같은 경계로 갈랐다면, 우리 아래 절반은 그것의
  다른 도메인 재현이다. 우리가 다를 수 있는 곳은 **LLM 쓰임새 자체(토큰 · 캐시 · 맥락 · 꺼냄)를 감지 대상으로 삼는 것**뿐일 수 있다.
- MAPE-K 계열의 **런타임 모형(models@runtime)** 문헌을 안 봤다 -- State Graph 가 거기 있는 것일 수 있다.
- LangSmith · Langfuse 가 점수를 런타임 라우팅에 쓰는 기능이 있는지 **문서를 안 열었다**(조각에는 없었다).
- OTel `gen_ai.evaluation.result` 는 Development 안정도다 -- 이름이 바뀔 수 있다. 우리 신호 이름은 MS 것으로 두고 짝만 둔다.
- 화이트리스트는 **지금 Sensor 판(d4b80b3)** 기준이다. Sensor 가 칸을 더하면 MS 는 그것을 모르는 칸으로 버린다(시험으로 붙든다) --
  조용히 날글이 들어오는 길을 막는 대신, 새 수 칸을 쓰려면 MS 쪽 화이트리스트를 고쳐야 한다.
