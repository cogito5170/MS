# 선행조사 -- LLM Policy Runtime (2026-10-01)

코드보다 먼저 커밋한다. 짓는 것: MS 를 provider(OpenAI · Claude · Gemini) **위의** 정책 런타임으로 넓힌다 --
provider 독립 요청 · 정규 텔레메트리 · 텔레메트리에서 모형이 해석한 상태 · 그 상태로 Context/Prompt/Provider Policy 를 고르고 ·
제안은 WALP 가 판정한다. 연구 질문:

> 텔레메트리에서 나온 상태로 Context Policy 와 Prompt Policy 를 동적으로 고르면, 고정 정책보다 품질을 지키면서
> 토큰 · 지연 · 재시도 · 비용을 줄이는가?

**이 조사는 얕다.** 아래는 전부 검색 조각만 보고 단 것이다(`[출처:조각]`). 전문을 읽은 것은 없다.

## 가장 가까운 선행연구

| 우리 설계의 부분 | 가장 가까운 것 | 확인수준 | 겹치는 것 · 다른 것 |
|---|---|---|---|
| **연구 질문 자체** | *Beyond Token Savings: A Systematic Study of Context Compression in LLM Agents* (arXiv:2609.32961, 2026-09-26, UT Austin) -- 압축을 **런타임 정책**으로 보고 성공 · 토큰 · 종단 지연 · 추정 비용을 ~35,000 실행에서 잼(SWE-bench Verified · Terminal-Bench, 오픈 모형 셋) | [출처:조각] | **거의 같은 물음이다.** 조각의 핵심 발견: Qwen/Terminal-Bench 에서 토큰을 ~1/3 쓰는 정책이 **20~80% 더 오래** 걸렸다. → 우리는 "토큰 감소 = 지연 감소" 를 가정하지 않고 둘을 따로 잰다(사전등록 H2 · H3 분리). 다른 것: 그들은 압축만, 오픈 모형만. 우리는 압축 정책을 **텔레메트리에서 나온 상태**로 고르고, 상용 provider 둘을 같은 과업에 놓고, 실행은 결정론적 중재자를 지난다 |
| 상태를 맥락에 싣는 에이전트의 토큰 줄이기 | *Reducing Token Usage of State-in-Context Agents using Minification* (arXiv:2606.01326) | [출처:조각] | 우리 COMPRESS(같은 열 머리 한 번 · 수 반올림)와 같은 부류. 제목만 봤다 |
| 학습된 맥락 압축 | Acon (arXiv:2510.00615) · Active Context Compression (arXiv:2601.07190) · AGORA (arXiv:2605.26596) | [출처:조각] | 압축기를 **배운다.** 우리는 결정론적 규칙(판본 붙음)이다 -- 재현 가능성이 목적. 대신 그들보다 덜 줄일 것이다 |
| **정규 텔레메트리 스키마** | OpenTelemetry GenAI semantic conventions -- `gen_ai.usage.input_tokens`(캐시 포함 전체 입력) · `gen_ai.provider.name` · `gen_ai.server.time_to_first_token` | [출처:조각] | **그대로 따른다**: canonical `input_tokens` 는 캐시 읽기를 **포함**한 전체 입력이다(Anthropic 의 `input_tokens` 는 캐시를 뺀 몫이라 더해야 한다). 다른 것: OTel 은 스팬 · 지표 규약이고 정책 · 상태 층이 없다. 우리 레코드는 OTel 이름으로 내보낼 수 있게 짝을 둔다 |
| provider 정규화 · 비용 추적 | LiteLLM (github.com/BerriAI/litellm) · Portkey · OpenRouter -- 100+ provider 를 OpenAI 꼴 한 인터페이스로, 지출 추적 · 예산 · 대체 | [출처:조각] | **어댑터 층은 이미 상품이다.** 우리 어댑터는 그것을 대신하려는 것이 아니라, 정책 층이 provider 모양에 안 물들게 하는 **경계**다. 다른 것: 그들은 OpenAI 꼴을 표준으로 삼는다 -- 우리는 어느 provider 꼴도 표준으로 삼지 않는다(원칙 10) |
| Provider Policy(라우팅) | RouteLLM (ICLR 2025, 선호 자료로 강/약 모형 라우터) · FrugalGPT (싼 것부터, 점수가 낮으면 올림) | [출처:조각] | 이번에는 **인터페이스만** 둔다. 명시 선택만 짓는다. "어느 provider 가 낫다" 를 가정하지 않는다 |

## 아직 못 지운 가능성

- **2609.32961 의 전문을 안 읽었다.** 그들이 이미 "상태(진행 정도 · 맥락 크기)에 따라 압축을 바꾸는" 적응 정책을 쟀다면 우리 질문의 절반은 답이 나와 있다.
  조각만으로는 고정 압축 정책들의 비교인지, 적응 정책도 있는지 모른다.
- DSPy · TextGrad 류의 **프롬프트 최적화**를 안 찾아봤다. 우리 Prompt Policy 는 최적화가 아니라 상태에 따른 규칙 선택이지만, 비교 기준으로 필요할 수 있다.
- LangSmith · Langfuse · Helicone 같은 관측 도구가 provider 정규화 텔레메트리 위에 정책을 얹는지 안 봤다.
- 우리 과업 모음은 **장난감**(서버 · 랙 세계)이다. 2609.32961 은 SWE-bench 다. 우리 수가 그쪽과 같은 방향이어도 일반화는 못 한다.
- 이 컨테이너에서는 OpenAI 키가 없고 api.openai.com 이 막혀 있다(프록시 403). **OpenAI 칸은 여기서 한 번도 진짜로 못 돌린다.**
